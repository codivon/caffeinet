## ۱) نقشهٔ وضعیت قبل (فاز ۱۲/۱۳-ب)

| مؤلفه | وضعیت قبل | مشکل برای هاست اشتراکی |
|---|---|---|
| `RealtimeStreamController` | احراز نشست/توکن + `$request->session()->save()` (فاز ۱۳) | بدون `session_write_close()` صریح؛ بدون `last_id` |
| `SseService::streamResponse` | حلقهٔ `while(true)` + `sleep(1)`؛ **TTL = ۲۴۰ ثانیه**؛ ضربان ۱۵ ثانیه؛ کوئری `realtime_events` در **هر تیک** (هر ثانیه) | هر اتصال تا ۴ دقیقه ورکر LSAPI را نگه می‌دارد؛ زامبی‌ها تا ۴ دقیقه؛ ۱ کوئری/ثانیه/اتصال |
| پایان استریم | `event: bye` (کلاینت گوش نمی‌داد!) | کلاینت پایان تمیز را مدیریت نمی‌کرد — فقط `onerror` عمومی |
| هدرها | `text/event-stream`, `no-cache`, `X-Accel-Buffering: no`, `Content-Encoding: none` | بدون `Connection: close`، بدون هدر LiteSpeed، بدون padding (خطر بافر LiteSpeed = تحویل توده‌ای رویدادها) |
| کلاینت `realtime.js` v7 | EventSource با اتصال مجدد خودکار مرورگر؛ بستن تب پنهان؛ fallback پولینگ صفحات از طریق `RT.onConnection(false)` | **هیچ ضدتندزنی‌ای**: خطا → مرورگر بی‌نهایت retry؛ ۴۰۱ (انقضای توکن) → `readyState=CLOSED` → SSE تا رفرش صفحه مُرده؛ حلقهٔ معیوب می‌توانست ورکرها را قحطی کند |
| رویدادهای بین reconnect | از دست می‌رفتند (هر استریم از `max(id)` شروع می‌شد) | gap چندثانیه‌ای بین دو استریم = رویداد گم‌شده |
| throttle روت | نداشت | حلقهٔ معیوب کلاینت = حملهٔ ناخواسته به ورکرها |

هر تیک قبل: ۱ کوئری `realtime_events` (ایندکس‌شده، سبک ولی هر ثانیه) + bootstrap لاراول فقط یک‌بار در هر استریم (۲۴۰ ثانیه) — نشست با `save()` رها می‌شد (فاز ۱۳ درست بود).

## ۲) تغییرات اعمال‌شده

### سمت سرور
- **`config/realtime.php` (جدید):** کانفیگ کوتاه‌چرخه — `REALTIME_SSE_TTL` (پیش‌فرض ۲۵s)، `REALTIME_HEARTBEAT` (۱۵s)، `REALTIME_SSE_TICK` (۱s)، `REALTIME_SSE_RETRY` (۲۰۰۰ms)، `REALTIME_SSE_PAD` (۲۰۴۸B)، `REALTIME_SSE_SWEEP` (۵s). همه در سرویس clamp می‌شوند (TTL: ۸–۳۶۰۰s).
- **`SseService::streamResponse`:**
  - **کوتاه‌چرخه:** پایان تمیز بعد از TTL با `event: close` + `data {"reason":"ttl","retry":2000}` (بجای «bye» ناموجود در کلاینت).
  - **`retry: 2000`** در ابتدای هر استریم → فاصلهٔ اتصال مجدد مرورگر کوتاه و کنترل‌شده.
  - **ضربان:** فوری + هر ۱۵ ثانیه (`event: ping`).
  - **تیک سبک کش‌محور:** `SseService::insert` بعد از هر رویداد `Cache::increment('rt:seq')` می‌زند؛ تیکِ استریم اول فقط شمارندهٔ کش را می‌خواند و فقط با تغییر شمارنده (یا هر ۵ ثانیه شبکهٔ ایمنی `sweep`) کوئری دیتابیس می‌زند → روی `CACHE_STORE=file` تیک‌های بی‌رویداد **صفر کوئری** دارند؛ رویداد واقعی همچنان در ≤۱ ثانیه push می‌شود (تست شد: emit در ثانیهٔ ۴ → تحویل همان تیک).
  - **replay با Last-Event-ID:** هر `rt` اکنون `id:` دارد؛ استریم با هدر `Last-Event-ID` یا `?last_id=` شروع می‌شود (clamp ≤ ۵۰۰۰ رویداد) → رویدادهای gap ریکانکت از دست نمی‌روند.
  - **`ignore_user_abort(false)` + `connection_aborted()` در هر تیک:** اولین نوشتن به سوکت مرده → خاتمهٔ فوری PHP → آزادشدن ورکر.
  - **هدرها:** + `Connection: close`، + `X-LiteSpeed-Cache-Control: no-cache` (+ قبلی‌ها)؛ **padding اولیهٔ ~۲KB** (کامنت SSE) برای عبور از بافر LiteSpeed.
- **`RealtimeStreamController`:** خواندن `last_id`/هدر + `session_write_close()` صریح (بعد از `session()->save()`) — قفل نشست تضمیناً قبل از استریم رها می‌شود.
- **`routes/web.php`:** `throttle:120,1` روی `/realtime/stream` (ضد حلقهٔ معیوب؛ استفادهٔ معمول ~۲-۴ اتصال در دقیقه).

### سمت کلاینت (`realtime.js` v8، cache-bust در ۵ لایه)
- **`event: close` → ریکانکت کنترل‌شدهٔ خودمان** (بستن es + تایمر `retry×jitter` ۰٫۷۵–۱٫۵) — gap کوتاه‌چرخه «قطعی» حساب نمی‌شود و صفحات بیدار نمی‌شوند.
- **طبقه‌بندی خطا:** خطای واقعی = بدون هیچ داده در ~۱۲ ثانیهٔ اول؛ چرخهٔ سالم (داده/ضربان/close) هرگز خطا حساب نمی‌شود → با TTL=۲۵s سیستم‌سالم تعلیق نمی‌شود.
- **۳ خطا در ۶۰ ثانیه → تعلیق SSE** با cooldown نمایی ۶۰s→۸m (jitter ضدگله) + `RT.connected=false` → صفحات خودکار به **پولینگ اضطراری** می‌روند (سازوکار موجود `onConnection`). پایان تعلیق → تلاش مجدد؛ موفقیت → صفر شدن شمارنده‌ها (**برگشت نرم به SSE**).
- **۴۰۱/۴۰۴ (`CLOSED`)**: قبلاً SSE تا رفرش مُرده می‌ماند → حالا es بسته و با backoff تلاش می‌شود.
- **`?last_id=`** روی هر ریکانکت (از `ev.lastEventId`) → صفر رویدادِ گم‌شده.
- تلاش اجباری در بازگشت به تب (گریس ۱۰ ثانیه‌ای) + reset تعلیق با رسیدن توکن تازه (`RT.setup`).

## ۳) ریاضی ظرفیت روی هاست اشتراکی (LiteSpeed/LSAPI)

هر اتصال SSE = **یک ورکر LSAPI تا پایان اتصال**. سقف معمول هاست: ~۲۰-۳۰ ورکر (Entry Processes).

```
ظرفیت همزمانِ نظری = ورکرها × (TTL + فاصلهٔ ریکانکت) / TTL
۲۵ ورکر، TTL=25s، ریکانکت=2s  →  ۲۵ × ۲۷/۲۵ ≈ ۲۷ اتصال
```

نکتهٔ صادقانه: ضریب کوتاه‌چرخه (×۱٫۰۸) بزرگ نیست — چون ورکر در فاصلهٔ ریکانکت هم بیکار نمی‌ماند بلکه به درخواست‌های عادی می‌رسد. **سود واقعی کوتاه‌چرخه سه چیز است:**
1. **درود زامبی:** تبِ بسته‌شدهٔ ناگهانی/پراکسی که سوکت را کشت — قبلاً تا ۲۴۰ ثانیه ورکر نگه می‌داشت؛ حالا ≤۲۵ ثانیه (و با `ignore_user_abort(false)` معمولاً ≤۱۵ ثانیه = اولین ضربان).
2. **bootstrap منظم:** هر اتصال هر ~۲۷ ثانیه چرخهٔ کامل lifecycle را طی می‌کند — نشت حافظه/قفل انباشته نمی‌شود.
3. **جمع‌شدن خودکار:** اگر ورکرها اشباع شوند، اتصال‌های جدید شکست می‌خورند → کلاینت به پولینگ اضطراری می‌رود → خودترمیمی به‌جای قحطی کل سایت.

**ظرفیت واقع‌بینانه (با حاشیهٔ ۳۰-۴۰٪ برای درخواست‌های عادی صفحات):**

| سقف ورکر هاست | SSE همزمانِ ایمن | توصیه |
|---|---|---|
| ۲۰ ورکر | ~۱۲-۱۵ | SSE قابل قبول برای پنل‌ها |
| ۳۰ ورکر | ~۲۰-۲۵ | SSE قابل قبول (پیش‌فرض TTL=25s) |
| ۵۰ ورکر | ~۳۵-۴۵ | SSE با پایش Entry Processes |
| ۱۰۰+ ورکر / VPS | ۱۰۰+ | SSE یا پوشر آزادانه |

> هدف ~۵۰-۸۰ همزمان SSE فقط روی هاست‌هایی با سقف ورکر ≥۸۰-۱۰۰ واقع‌بینانه است؛ روی ۲۰-۳۰ ورکر سقفِ فیزیکی همان ۲۰-۳۰ اتصال است — این محدودیت **ساختاری LSAPI** است و هیچ تنظیم PHP آن را برنمی‌دارد.

**برای ~۵۰۰ همزمان — توصیهٔ نهایی (به ترتیب):**
1. **پولینگ + بیدارباش (روش ۱):** درخواست هر ۱۵-۳۰ ثانیه (تب پنهان کندتر) — صفر ورکر دائمی؛ ۵۰۰ کاربر ≈ ۱۶-۳۳ req/s — برای ۴ هسته قابل تحمل. «آنی» بودن کمتر است ولی سیستم هرگز نمی‌میرد.
2. **پوشر با سرور خودمیزبان (Soketi/Reverb) روی یک VPS ارزان (~۲$/ماه):** سوکت واقعی، ۵۰۰+ اتصال روی یک پروسهٔ Node؛ PHP فقط هنگام رویداد trigger می‌شود. تنظیمات ← Realtime ← «سوکت خارجی پوشر» + هاست سفارشی. (pusher.com از ایران ناپایدار است.)
3. **VPS ارزان برای کل realtime:** همان VPS می‌تواند Soketi + در آینده وب‌سوکت اختصاصی را بگیرد؛ هاست اشتراکی فقط HTTP عادی سرو می‌کند.
4. **ترکیب پیشنهادی نهایی برای پروداکشن فعلی:** پنل‌های پشتی (تعداد کم، ~۱۰-۲۰ همزمان) = SSE داخلی؛ اپ مشتری (۵۰۰ همزمان) = پولینگ یا پوشرِ VPS.

## ۵) تست‌ها (همه ✓)

1. **دو چرخهٔ کامل TTL با curl** (توکن Sanctum): چرخهٔ ۱: TTFB=۱٫۰s، padding+`retry: 2000`+ping فوری+ping@۱۵s+`event: close`@۲۵s، پایان تمیز ۲۶٫۰s. چرخهٔ ۲: TTFB=۰٫۱۵s، close@۲۵٫۲s.
2. **replay:** درج رویداد id=۸ → اتصال با `?last_id=7` → رویداد با `id: 8` و payload صحیح تحویل شد.
3. **push لحظه‌ای:** emit در ثانیهٔ ۴ استریم → تحویل در همان تیک (id: 9) — الگوی رویدادمحور حفظ شده.
4. **مرورگر (agent-browser، ادمین):** `RT.connected=true`، دقیقاً **۱ اتصال استریم به‌ازای هر تب** (تأیید `ss`: ۲ تب = ۲ اتصال)، ریکنکت هر ~۲۷ ثانیه در server.log، بدون خطای کنسول؛ خطای گذرا → خودترمیمی به SSE. اسکرین‌شات: `shots/59c-admin-sse-connected.png`، `59c-admin-sse-stable.png`.
5. **حالت پولینگ:** سوییچ تنظیمات → رفرش ادمین → `RT.active=false`، صفر درخواست stream از آن تب، `/admin/notifications/badge` و `/admin/announcements/pending` پول می‌شوند. اسکرین‌شات: `shots/59c-admin-polling-mode.png`. (تنظیمات به «sse» برگردانده شد.)
6. **بنچمارک TTFB (`time_starttransfer`):** قبل ۰٫۱۹s (ران گرم؛ ران‌های همزمان با تست بار ایجنت دیگر ۱٫۵-۲٫۱s) → **بعد ۰٫۱۵-۰٫۲۱s** — padding هیچ هزینهٔ محسوسی ندارد؛ بهبود اصلی: اشغال ورکر از ۲۴۰s به **۲۵s**.
7. بدون خطای جدید در `laravel.log`؛ `php -l` و `node --check` همه سبز.

## ۶) تأیید نهایی (اجرای پایانی — همهٔ موارد بخش ۵ دوباره اجرا و سبز شد)

- **دو چرخهٔ TTL با curl (نشست ادمین):** چرخهٔ ۱: `retry: 2000`+`ping` فوری، `ping@15s`، `event: close`+`{reason:ttl,retry:2000}`@25s، پایان تمیز exit=0. چرخهٔ ۲: ریکانکت همان ثانیه، `ping` فوری، `close`@25s — دو بستن تمیز پشت‌سرهم ✓
